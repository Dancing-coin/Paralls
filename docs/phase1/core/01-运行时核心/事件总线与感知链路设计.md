# 事件总线与感知链路设计

## 0. 架构视图（系统 / 子系统 / 孙系统）

### 0.1 总体架构设计

事件总线与感知链路是《开本》的跨层消息骨架，负责“事实传输 + 感知编译 + 角色私有裁剪”。

```text
┌─────────────────────────────────────────────────────────────┐
│                 事件总线与感知链路完整架构                  │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  L1 确定性空间层（原始事件生产）                     │   │
│  │                                                      │   │
│  │  · 客户端交互系统事实上抛                            │   │
│  │  · 空间音频听觉事实上抛                              │   │
│  │  · ESM 环境状态变化事实上抛                          │   │
│  └──────────────────────────────────────────────────────┘   │
│                            │                                 │
│                            ▼                                 │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  L6 跨层基础设施层（事件总线治理）                   │   │
│  │                                                      │   │
│  │  · 事件总线内核（路由/优先级/TTL/背压）              │   │
│  │  · 实时通道（P0/P1）                                 │   │
│  │  · 可靠通道（可重试/可审计/可持久）                  │   │
│  └──────────────────────────────────────────────────────┘   │
│                            │                                 │
│                            ▼                                 │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  L2 智能决策层（感知转换）                           │   │
│  │                                                      │   │
│  │  · 可感知信息编译层（候选感知事件生成）              │   │
│  │  · Per-Character 感知过滤器（角色私有裁剪）          │   │
│  │  · 输出：角色感知事件                                │   │
│  └──────────────────────────────────────────────────────┘   │
│                            │                                 │
│                            ▼                                 │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  消费层（角色 / 司命）                               │   │
│  │                                                      │   │
│  │  · 角色默认消费角色感知事件                          │   │
│  │  · 司命消费原始/结构化世界事件                      │   │
│  │  · 司命回写仅限高层催化消息                         │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

系统边界：

- 事件总线只做传输与治理，不做业务推理
- 编译层负责“候选事件生成”
- 过滤器负责“角色私有裁剪”

### 0.2 系统分解

#### 0.2.1 子系统：事件总线内核

职责：消息接收、路由、优先级、背压、通道分流。  
孙系统：路由器、优先级调度器、TTL 管理器、背压降级器。

#### 0.2.2 子系统：实时通道

职责：承载 `P0/P1` 低延迟消息。  
孙系统：实时会话管理器、快速分发器、瞬态缓冲器。

#### 0.2.3 子系统：可靠通道

职责：承载可重试、可审计、可持久消息。  
孙系统：可靠队列管理器、重试器、死信处理器。

#### 0.2.4 子系统：可感知信息编译层

职责：把原始世界事件编译为多感官候选感知事件。  
孙系统：通道编译器、上下文融合器、阶段标签器。

#### 0.2.5 子系统：Per-Character 感知过滤器

职责：基于角色档案裁剪候选事件，产出角色感知事件。  
孙系统：感官启用检查器、空间遮挡判定器、状态修正器。

### 0.3 核心接口约束

- 输入：`L1/ESM/空间音频` 上抛的精确世界事件
- 输出：司命原始事件视图、ESM结算输入、角色感知事件、高层消息通道
- 非职责：证据解释、角色推理、叙事判断替代

## 1. 设计目标与非目标
### 1.1 设计目标

本文档用于冻结《开本》事件总线和感知链路的当前可执行方案，明确：

- 事件总线的职责边界
- 世界事件、感知事件、司命高层消息三类对象的区别
- `L1 / ESM / 司命 / 角色智能体` 的统一消息矩阵
- 实时通道与可靠通道的拆分规则
- 可感知信息编译层与角色感知过滤器的分工边界
- Per-Character 感知过滤器的工作方式
- 空间音频、视觉、嗅觉、热感等如何转成角色可感知事件

本文档当前冻结的是语义层和链路层，不是最终二进制线协议。

### 1.2 非目标
本节以当前阶段范围约束为准，完整延后能力见第 8 节。

## 2. 系统边界（上游 / 下游 / 禁止越权）

### 2.1 L1 的定位前提

当前不采用“`L1` 只是普通 Godot 客户端，AI 输入后补适配”的理解。

当前采用：

- `L1` 既负责传统 3D 渲染、物理、音频、UI
- 也负责把世界中的行为与状态变化结构化上抛
- 同时承接来自 `L2` 的角色行动和环境执行指令

这意味着事件总线不是外挂在客户端旁边的附属件，而是 `L1` 架构职责的一部分。

### 2.2 事件总线是什么

事件总线是 `L1`、`L2`、`L3` 之间的通信中枢。

它负责：

- 消息接收
- 路由
- 优先级调度
- 广播 / 单播 / 组播
- 实时通道与可靠通道分流
- 必要的事件持久化和重放入口

### 2.3 事件总线不是什么

它不负责：

- 判定证据真伪
- 计算角色是否说谎
- 判断痕迹应该如何生成
- 替代司命或角色智能体做业务推理
- 代替 `ESM` 做环境物理结算

### 2.4 感知链路是什么

感知链路是从 `L1` 原始世界状态，到“某个具体角色此刻能感知到什么”的转换过程。

关键不是把整个世界复制给 AI，而是只把该角色在物理上可知的信息转换成结构化感知事件。


### 2.5 司命与角色不是同一订阅面

当前不采用“总线把同一份内容原样广播给司命和所有角色”的理解。

当前采用：

- 司命订阅更广的原始/结构化世界事件
- 角色订阅过滤后的专属感知事件
- 这层差异是信息不对称、公平性和知识博弈成立的前提

### 2.6 ESM 不做证据解释

`ESM` 上报的是：

- 门被烧坏
- 窗帘烧毁
- 棉花团由燃烧转为潮湿
- 水缸水温上升

不是：

- “这构成了关键物证”
- “上校纵火了”
- “这是嫌疑矛盾”

证据解释属于司命事实核心和角色 `L2` 理解层。

### 2.7 司命不能借总线低层控角

司命不能通过总线直接下发：

- 去到坐标 `X`
- 现在杀死 `Y`
- 立刻拿走 `Z`

司命能发的只有：

- `impulse`
- `fact_reveal`
- `opportunity`

并且仍要经过角色自己的 `L2/L3` 与三重过滤器。

## 3. 消息对象分层

这是当前版本最关键的收束点。

### 3.1 原始 / 结构化世界事件

它表达世界中实际发生了什么。

典型内容：

- 谁在什么位置
- 用什么对什么做了什么
- 接触点、落点、命中点
- 造成了什么物理状态变化
- 哪些感官在理论上可以感知到

典型消费者：

- `ESM`
- 司命事实核心
- 物品流转追踪器
- 接触痕迹 / 生物痕迹相关系统
- 审计与复盘系统

### 3.2 角色感知事件

它表达“这个角色此刻看到了 / 听到了 / 闻到了 / 感觉到了什么”。

它不是原始世界事件的原样转发，而是经过：

- 感官启用检查
- 距离判断
- 物理遮挡
- 环境干扰
- 状态修正

之后的结果。

典型内容：

- 我看到有人在实验台前点火
- 我听到一声轻微的“噗”声
- 我闻到焦糊味
- 我感觉到近处有热辐射

### 3.3 司命高层消息

这是司命发给角色的高层催化对象。

当前稳定类型是：

- `impulse`
- `fact_reveal`
- `opportunity`

它们的本质是：

- 倾向
- 唤醒
- 机会
- 事实提示

而不是动作控制。


当前冻结的是语义字段集合，不是最终编码格式。

### 3.4 顶层公共字段

所有事件都应至少包含：

- `event_id`
- `event_type`
- `timestamp`
- `priority`
- `source`
- `routing`
- `payload`

### 3.5 `source`

至少表达：

- 来源层级（`L1 / L2 / L3 / system`）
- 来源组件
- 发起角色 / 对象 ID

### 3.6 `routing`

至少表达：

- 路由模式（广播 / 单播 / 组播 / 发布订阅）
- 作用域（房间 / 场景 / 子区域）
- 目标集

### 3.7 `payload`

由事件类型决定，但对空间世界事件，必须尽量精确。


结合 `352/353`，当前世界事件不接受“有人做了某事”这类模糊表述。

至少应表达：

- 谁在做
- 在哪里做
- 用什么做
- 对什么做
- 从哪里发起
- 作用点在哪里
- 造成了什么状态变化
- 哪些感官可以感知到

### 3.8 精确空间字段

对于需要物理结算和证据追踪的事件，建议至少包含：

- 发起者位置
- 目标位置
- 作用发起点
- 接触点 / 落点 / 命中点
- 方向 / 朝向
- 环境条件

### 3.9 结果字段

至少包含：

- 原状态
- 新状态
- 变化进度（若持续）
- 连带效果

### 3.10 感知范围字段

对于可被感知的事件，需要显式给出各感官作用范围，例如：

- `visible_range`
- `audible_range`
- `smell_range`
- `thermal_range`

### 3.11 字段分层表（总线侧冻结）

当前需要把“公共信封字段”“司命确认字段”和“不应出现在总线侧的字段”严格分层，避免把会话社会语义或角色主观状态混进底层事实流。

#### 公共信封字段

以下字段属于跨模块运行时契约，应放在事件总线公共信封中：

- `event_id`
- `event_type`
- `room_id`
- `scene_id`
- `zone_id`
- `source.layer`
- `source.system`
- `source.actor_id`
- `source.object_id`（如有）
- `routing.audience_mode`
- `routing.routing_mode`
- `routing.dialog_group_id`（如有）
- `routing.target_ids`（如有）
- `priority`
- `ttl`
- `durability`
- `producer_ts`
- `causation_id`
- `correlation_id`
- `payload`

可选扩展：

- `sequence_domain`
- `dedupe_key`

这些字段回答的是：

- 这是什么事件
- 它来自哪里
- 它属于哪一局 / 哪一场景 / 哪一区域 / 哪一对话组
- 它应如何传播

#### 司命确认字段

以下字段不是原始世界事实，而是司命高阶知识图谱基于原始事实给出的会话关系确认结果。若需回写，应作为独立事件类型的 `payload` 出现，而不是反向污染原始事实事件：

- `conversation_id`
- `conversation_role_state`
- `knowledge_confirm_level`
- `join_transition_result`
- `exclusion_result`
- `rejoin_result`
- `conversation_open_level`（如需）
- `mutual_awareness_confirmed`（如需）

这层回答的是：

- 基于事实与高阶知识推理后，这个角色在当前会话中的社会语义位置是什么

#### 会话确认事件（最小语义 schema）

当前最小会话确认事件建议先冻结三类：

- `MembershipResolution`
- `AccessResolution`
- `KnowledgeResolution`

它们都继承公共信封，不另造外壳，当前只冻结 `payload` 语义，不冻结最终编码格式。

`MembershipResolution.payload` 至少包含：

- `conversation_id`
- `actor_id`
- `membership_role_state`
- `previous_membership_role_state`（如有）
- `membership_started_at`
- `last_state_changed_at`
- `join_path`
- `mutual_awareness_confirmed`
- `exclusion_signal_level`

它回答的是：

- 某角色当前在这场会话中的成员身份是什么

`AccessResolution.payload` 至少包含：

- `conversation_id`
- `actor_id`
- `information_item_id`（如有）
- `access_quality`
- `access_started_at`
- `access_modalities`
- `access_path`
- `bounded_by_private_context`

它回答的是：

- 某角色是否真正接入了这场会话或其中某条信息，以及从什么时候开始接入

`KnowledgeResolution.payload` 至少包含：

- `information_item_id`
- `actor_id`
- `knowledge_state`
- `knowledge_started_at`
- `knowledge_source`
- `derived_from_access_quality`
- `supersedes_previous_state`（如有）

它回答的是：

- 某角色当前对某条信息到底处于什么知识状态，以及这种状态如何形成

顺序约束：

- `AccessResolution` 不回答成员资格
- `MembershipResolution` 不回答具体知道了什么
- `KnowledgeResolution` 不得跳过 `AccessResolution` 的时间边界
- 这三类事件不能被折叠成一类“全知确认包”

#### 不应出现在总线侧的字段

以下内容不应出现在 `L1` 原始事实上抛或总线公共信封中：

- “某人已经成为正式会话成员”这类未经司命确认的高阶结论
- “A 知道 B 知道自己在场”这类高阶知识真值
- 角色主观怀疑值、压力解释结果、内心独白
- 全局高阶知识图谱快照
- 角色本地完整会话历史或整段对话文本回放

边界强调：

- `L1/ESM` 负责生产原始会话事实
- 事件总线负责承载公共信封
- 司命负责回写会话关系确认结果
- 总线本身不推断成员资格，也不承载角色主观层

## 4. 通道与治理

### 4.1 为什么不能只用一个中间件

《开本》的消息存在明显异构：

- 有些消息要求极低延迟
- 有些消息要求高可靠
- 有些消息吞吐极高，但可容忍偶尔丢失
- 有些消息只需要最终持久化，不需要实时送达

因此当前不采用“一个 MQ 吃掉全部场景”的方案。

### 4.2 当前采用的通道拆分

#### 实时通道

负责：

- 客户端实时交互
- `P0 / P1` 控制消息
- 高频状态同步
- 感知心跳与高频流式更新

当前技术方向：

- 客户端 ↔ 服务端：`WebSocket`
- 服务端内部超低延迟分发：`内存队列 / 本地直连`

#### 可靠通道

负责：

- 异步 AI 推理请求
- 跨服务解耦
- 事件持久化入口
- 审计、复盘和重放数据

当前技术方向：

- `NATS / JetStream`

### 4.3 最终持久化

最终用于：

- 事件日志
- 审计
- 复盘
- 状态回放

当前方向：

- `PostgreSQL`


### 4.4 事件分类

至少分为以下几类：

- 玩家行为事件
- AI 行为事件
- 环境与物理事件
- 感知结果事件
- 司命叙事事件
- 系统状态事件
- `L3` 视觉增强请求事件

### 4.5 优先级口径

当前采用四级优先级：

- `P0`：致命、本能反应、硬中断
- `P1`：玩家交互、角色关键动作、状态同步
- `P2`：普通感知、AI 常规行为、对话推进
- `P3`：环境背景变化、`L3` 触发、非关键异步处理

### 4.6 典型优先级映射

| 优先级 | 典型事件 | 处理要求 |
| :--- | :--- | :--- |
| `P0` | 暗杀意图、近身威胁、本能反应触发 | 直接走实时通道，最短路径处理 |
| `P1` | 玩家说话、拾取、展示、投票、角色关键动作 | 优先实时送达 |
| `P2` | 感知更新、普通 AI 行为、普通对话结果 | 实时通道内正常排队 |
| `P3` | 环境背景事件、`L3` 请求、复盘附加事件 | 可延后或异步处理 |

补充说明：

- 并非所有 `L3` 请求都固定为 `P3`。与关键叙事节点绑定、且有严格时效要求的视觉请求可提升到 `P1/P2`。
- `L3` 请求优先级由司命叙事层判定，`L3` 执行层负责策略选择与降级。


### 4.7 TTL 原则

不是所有消息都值得排队等到送达。

因此当前采用 TTL 思路：

- 高时效低价值消息超时可丢弃
- 低频关键消息不能过期丢弃

### 4.8 批处理原则

适用于：

- 高频感知更新
- 多对象状态变更
- 心跳式全量同步

### 4.9 背压与降级

当客户端或角色侧积压过高时，可降级为：

- 减少高频推送
- 优先保留关键事件
- 从实时细粒度更新降为心跳补全

### 4.10 Phase 0 / 1 实现优先级

当前先做：

- `WebSocket` 主链路
- 基础广播 / 单播 / 组播
- 视觉 + 听觉的结构化事件
- 精确空间事件的最小字段集
- 司命 / 角色 / `ESM` 的消息对象分层

后续再补：

- 更细的嗅觉 / 热感扩散模型
- 更复杂的序列化优化
- 完整重放与压测体系

## 5. 路由与订阅规则

### 5.1 广播

发送给房间或场景内全部订阅者。

典型场景：

- 公共对话
- 公共环境事件
- 房间状态变更

### 5.2 单播

发送给某个指定接收者。

典型场景：

- 耳语文本结果
- 司命发给某个角色的 `impulse`
- 结局时的私有提示

### 5.3 组播

发送给一组满足条件的角色。

典型场景：

- 清晰区内所有可听见角色
- 某个区域内所有可看见火光角色
- 某阵营共享的私有事件

### 5.4 发布 / 订阅

用于跨服务异步订阅。

典型场景：

- 司命订阅关键事件
- `L3` 订阅高光触发事件
- 持久化服务订阅日志事件

### 5.5 会话路由的补充冻结

当前运行时会话机制采用四层作用域：

- `room`：单局运行时会话容器，只负责隔离，不作为普通角色对话默认传播面
- `scene`：房间内承载公开传播的空间单元
- `zone`：场景内用于局部传播、偷听与感知裁剪的局部范围
- `dialog_group`：运行时临时会话组，用于耳语、密谈、阵营共享或限定对象沟通

默认传播规则：

- 普通公开发言优先走 `scene`
- 普通近距聊天优先走 `zone`
- 耳语与密谈优先走 `dialog_group`
- `room` 只保留给阶段切换、房间状态变更等系统级广播

边界强调：

- 听见不等于加入对话
- 加入对话不等于补发更早历史
- 沉默在场者可以成为会话成员
- 偷听成功不自动授予成员资格

因此，对话传播的推荐主链是：

`说话行为事件 -> 路由作用域确定 -> 候选听觉事件生成 -> Per-Character 感知过滤 -> 角色实际听觉结果`

而不是“文本直接广播给所有订阅者”。

### 5.6 会话加入与偷听的边界

当前采用：

- 公开与局部会话：满足接入条件后，一旦发声即可自动加入
- 私密会话：进入范围后先成为候选接入者，不自动获得成员资格
- 新加入者只能从自己实际听到的时间点开始获得上下文，不补发更早历史

成员资格不由总线直接判定，而是依赖三件事共同成立：

- `L1` 上抛的空间接入与声学事实已成立
- 司命高阶知识图谱确认互相知晓已成立
- 当前未被排斥

总线在其中只负责：

- 传输接近、停留、退开、发声、门窗开合、遮挡变化、音量变化等原始事实
- 传输由司命回写的成员资格变化结果

总线不负责：

- 自己推断谁已经被纳入会话
- 自己推断谁知道别人知道自己在场
- 自己给新成员补发会话早期历史内容

## 6. 感知链路实现

这是当前方案的关键部件。

### 6.1 定义

每个角色都有一个独立的感知过滤器实例。

它不做业务推理，只做一件事：

把可感知信息编译层产出的候选事件，裁剪成“这个角色此刻能感知到什么”。

### 6.2 五步过滤流程

#### Step 0 候选事件接入

输入来自可感知信息编译层的候选事件，不直接消费全量原始世界事件。

#### Step 1 感官启用检查

例如：

- 盲人角色视觉禁用
- 听觉异常角色听觉增强
- 特殊角色启用额外感官

#### Step 2 空间范围检查

判断该事件是否在该角色对应感官的作用范围内。

#### Step 3 物理遮挡检查

判断门、墙、玻璃、家具、材质等是否改变感知结果。

#### Step 4 状态与注意力修正

根据角色当前状态调整结果，例如：

- 高压力忽略次要信息
- 醉酒导致模糊
- 专注时更容易漏掉非注意方向的信息
- 致幻时可能产生异常感知

#### Step 5 生成角色专属感知事件

输出给该角色的 `L1` 感知层，而不是把原始世界事件直接塞给角色。

### 6.3 它不是可选中间件

Per-Character 感知过滤器不是一个“后续再优化”的可选层。

它是当前消息边界的一部分：

- 没有它，角色就会默认看到同一份世界
- 没有它，嗅觉 / 热感 / 遮挡 / 距离 / 门缝 / 朝向差异都无法工程化表达
- 没有它，司命与角色之间也无法维持必要的信息不对称


每个角色都要有感知档案。

至少包括：

- 视觉
- 听觉
- 触觉
- 嗅觉
- 热感
- 特殊感官（如有）

每种感官至少要定义：

- 是否启用
- 基础范围
- 灵敏度
- 细节等级或清晰度阈值
- 受状态影响的修正方式


### 6.4 视觉

AI 不接收截图，而接收结构化的“可见对象 / 可见事件”。

至少包含：

- 对象类型
- 位置与距离
- 状态
- 可见显著特征
- 可执行交互

### 6.5 听觉

听觉事件至少应包含：

- 声源
- 声音类型
- 清晰度
- 距离
- 方向
- 若为说话，文本与情绪

清晰度至少区分：

- `clear`
- `muffled`
- `distant`
- `barely_audible`

### 6.6 嗅觉

嗅觉不是视觉 / 听觉的附属品，必须单独建模。

典型可感知内容：

- 血腥味
- 烟雾
- 焦糊味
- 药味
- 香水味
- 潮湿和腐败气味

嗅觉事件应表达：

- 气味类型
- 强度
- 大致来源方向
- 扩散趋势

### 6.7 热感

热感用于补充：

- 火焰
- 热水
- 人体热源
- 尸体冷却
- 风口冷源

热感事件应表达：

- 热 / 冷类型
- 强度
- 距离
- 方位

### 6.8 触觉

用于：

- 接触
- 震动
- 纹理
- 温度
- 重量与形状


空间音频不仅要给人类玩家输出音频流，也要给 AI 角色输出结构化听觉事件。

当前冻结口径：

- 空间音频是 `L1` 子系统（`Steam Audio + Godot`），不是事件总线子系统。
- 事件总线只转发听觉相关世界事实，不负责音频信号处理。
- 可感知信息编译层负责把听觉事实编译为候选听觉事件，Per-Character 感知过滤器负责角色私有裁剪。

### 6.9 人类侧输出

- `HRTF / 距离衰减 / 遮挡 / 混响` 处理后的音频流

### 6.10 AI 侧输出

- 结构化听觉事件

推荐字段：

```json
{
  "event_type": "audio_event",
  "source_id": "char_02",
  "sound_type": "speech",
  "content": "我昨晚在书房看到了一个人影...",
  "clarity": "clear",
  "distance": 3.5,
  "direction": "front-left",
  "occlusion": "none",
  "reverb_zone": "study_room",
  "emotion": "nervous",
  "timestamp": "2026-05-20T19:05:30Z"
}
```

字段说明：

- `clarity`：`clear/muffled/distant/barely_audible/silent`
- `direction`：角色本地坐标系方位，不是世界绝对角度
- `occlusion`：遮挡强度分级
- `content`：仅在语音类型且可辨识时存在

### 6.11 AI 听觉输入流程

```text
L1 空间音频系统捕获声音事件
  -> 上抛听觉相关世界事实
  -> 事件总线路由
  -> 可感知信息编译层生成候选听觉事件
  -> Per-Character 感知过滤器按听觉档案/遮挡/状态裁剪
  -> 输出角色专属听觉事件到角色 L1 感知层
  -> 角色 L2 理解层解读
```

### 6.12 AI 语音输出流程

```text
角色 L4 生成对话文本与情绪参数
  -> 经事件总线发送到 L1 语音执行侧
  -> TTS 合成音频并绑定角色 3D 声源
  -> Steam Audio 空间化渲染
  -> 人类玩家听到空间语音
  -> 同步上抛听觉相关世界事实供其他角色感知
```

### 6.13 区域划分

当前采用：

- 清晰区
- 模糊区
- 静默区

耳语模式下，清晰区进一步缩小。

### 6.14 环境噪音作用

环境噪音会改变：

- 听觉范围
- 清晰度判定
- 偷听可行性
- 暗杀和密谈风险

### 6.15 耳语与偷听规则

- 耳语通过缩小传播半径与调整衰减曲线实现。
- 清晰区/模糊区/静默区在耳语模式下整体内收。
- 旁观者进入近距可触发“偷听到模糊内容”。
- 耳语双方可接收“有人靠近”提示事件，用于博弈反馈。


当前动作至少拆成三阶段：

- `action_intent`
- `action_executing`
- `action_completed`

意义：

- 角色可以在意图阶段就反应
- 不必等动作完成才知道危险已经发生

这对：

- 暗杀
- 拾取关键物品
- 展示证据
- 开关门

都非常关键。

## 7. 核心数据流与典型消息流

### 7.1 总矩阵

| 发送方 | 接收方 | 消息对象 | 是否原始世界事件 | 是否可直接做业务解释 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `L1` 交互 / 场景层 | 事件总线 | 精确世界事件 | 是 | 否 | 当前事实底座入口 |
| 事件总线 | `ESM` | 精确世界事件 | 是 | 否 | 用于物理结算与状态机更新 |
| 事件总线 | 司命 | 精确世界事件 / 系统事件 | 是 | 是，但由司命自身完成 | 用于事实、知识、叙事判断 |
| 事件总线 | 可感知信息编译层 | 精确世界事件 | 是 | 否 | 统一编译为候选感知事件 |
| 可感知信息编译层 | `Per-Character` 感知过滤器 | 候选感知事件 | 否 | 否 | 角色私有裁剪入口 |
| 感知过滤器 | 角色智能体 `L1` | 角色感知事件 | 否 | 是，但由角色 `L2/L3` 完成 | 角色默认入口 |
| 司命 | 事件总线 | `impulse / fact_reveal / opportunity` | 否 | 否 | 只是高层催化发送 |
| 事件总线 | 角色智能体 | 司命高层消息 | 否 | 是，但仍需过 `L2/L3` | 不能变成低层控制命令 |
| `ESM` | 事件总线 | 环境状态变化事件 | 是 | 否 | 只上报状态变化，不解释证据意义 |
| 事件总线 | 司命 / 可感知信息编译层 / 相关子系统 | 环境状态变化事件 | 是 | 各自解释 | 司命与角色视角不同 |

### 7.2 当前统一规则

- `L1` 上抛的是“世界发生了什么”
- `ESM` 接收的是“物理上应如何结算”
- 司命接收的是“全局事实链路发生了什么”
- 角色接收的是“我感知到了什么”
- 司命回写的是“我被催化去注意什么 / 倾向什么 / 想起什么”

不能把这几层混成一个广播对象。


### 7.3 玩家公共对话

```text
玩家发言
  -> L1 采集位置、模式、文本、声源参数
  -> 事件总线
  -> 空间音频侧输出人类音频流
  -> 可感知信息编译层生成听觉候选事件
  -> 感知过滤器为每个角色生成不同清晰度的听觉事件
  -> 角色 L1 感知层接收
  -> L2 理解层更新知识状态
```

### 7.4 玩家点燃物体

```text
玩家在精确位置使用打火机点燃目标
  -> L1 生成精确原始世界事件
  -> 事件总线分发给 ESM / 司命 / 证据相关子系统
  -> ESM 结算燃烧状态并回抛环境状态变化
  -> 物品流转与痕迹系统记录
  -> 可感知信息编译层生成视觉 / 听觉 / 嗅觉 / 热感候选事件
  -> 感知过滤器为每个角色分别生成视觉 / 听觉 / 嗅觉 / 热感事件
  -> 角色 L1 接收角色专属感知结果
  -> 角色 L2 更新理解
  -> 司命记录全局事实和知识传播后果
```

### 7.5 司命催化

```text
司命评估需要催化
  -> 通过可靠通道或实时通道发出高层消息
  -> 角色收到 impulse / fact_reveal / opportunity
  -> 角色按自身心智模型和三重过滤器决定是否响应
```

## 8. Phase 1 范围与延后项

后续所有实现与文档都应默认采用以下口径：

- 事件总线是传输层，不是业务判断层
- 真实世界事件必须尽量精确，不接受过粗抽象
- AI 感知世界依赖结构化语义事件，不依赖截图主路
- `ESM`、司命、角色不是同一订阅面
- 感知链路统一为“原始世界事件 -> 可感知信息编译层 -> Per-Character 感知过滤器 -> 角色感知事件”
- 每个角色都必须通过自己的感知过滤器看到不同的世界
- 司命发给角色的只能是高层消息，不能借总线直接控制低层动作
- 空间音频同时服务人类耳朵和 AI 听觉模型
- 嗅觉、热感、触觉不是附属字段，而是独立感知通道

### 8.1 云地部署补充规则

当任务在本地与云端之间切换时：

- 事件语义保持不变
- 路由分层保持不变
- 角色感知过滤责任保持不变
- 司命高层消息边界保持不变

即：云地调度是部署层策略，不是消息模型改版。


当前不在本版冻结范围内：

- 最终二进制线协议与序列化框架
- `WebSocket` 之外的传输层替代实现
- 所有感官的精细扩散数学模型
- 跨区域、跨服级消息编排

### C.1 事件总线子系统与孙系统（运行时冻结）

在本阶段，事件总线维持三块核心能力：

- 事件总线内核：路由器、优先级调度器、TTL 管理器、背压降级器
- 实时通道：实时会话管理器、快速分发器、瞬态缓冲器
- 可靠通道：可靠队列管理器、重试器、死信处理器

说明：

- 保持“实时 + 可靠”双通道，不退回单中间件方案
- 事件总线仍只承担传输与治理，不承担业务解释

### C.2 感知链路的编译与私有裁剪分工（补充冻结）

沿用主链路：

`原始世界事件 -> 可感知信息编译层 -> Per-Character 感知过滤器 -> 角色感知事件`

补充吸收以下未冲突组件：

- 可感知信息编译层：通道编译器、上下文融合器、阶段标签器、跨通道融合器
- 跨通道融合器孙系统：
  - 时间窗口管理器
  - 空间关联检测器
  - 融合规则引擎
  - 置信度计算器
  - 融合事件生成器

分工不变：

- 编译层负责候选事件构建与融合
- 过滤器负责角色私有裁剪，不与编译层合并

### C.3 L1 原始感知事实上抛器（八类口径）

本阶段接受“八类原始感知事实上抛器”作为 L1 输入侧展开口径：

- 视觉事实上抛器
- 听觉事实上抛器
- 触觉事实上抛器
- 热感事实上抛器
- 嗅觉事实上抛器
- 生理状态事实上抛器
- 社交距离与空间行为上抛器
- 角色状态事实上抛器

边界强调：

- 它们只负责原始事实采集与上抛，不负责候选感知编译
- 候选事件统一由可感知信息编译层生成

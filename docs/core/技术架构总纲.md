# 技术架构总纲

## 状态

- 状态：第一版初稿
- 主来源轮次：`203`、`214`、`215`、`260`、`302-303`、`307`、`379`、`380`、`400`
- 补充来源轮次：`031`、`040`、`212-213`、`286-291`、`310`、`352-353`

## 1. 文档目标

本文档用于冻结《开本》当前可执行的总体技术架构，明确各层职责、核心子系统边界、消息流向、基础设施选择与 Phase 边界。

本文档不是实现细节文档，不覆盖每个模块的全部字段设计；其职责是建立统一的系统地图，避免后续模块设计互相打架。

## 2. 架构目标

当前架构必须同时满足以下目标：

- 支撑 Phase 1 的动态剧本杀完整闭环
- 让 AI 角色与人类玩家在同一世界规则下互动
- 保证实时性、逻辑一致性与可扩展性
- 为 Phase 2/3 的跨局叙事和持续世界预留演进空间
- 避免为了远期能力破坏当前最小可行闭环

## 3. 顶层原则

### 3.1 分层原则

采用三层架构：

- `L1` 确定性空间层
- `L2` 智能体交互层
- `L3` 视觉增强层

分层不是展示用途，而是职责边界：

- `L1` 负责世界舞台和确定性执行
- `L2` 负责角色与叙事的自主决策
- `L3` 负责关键节点的表现强化

### 3.2 决策与执行分离

- 司命做秒级叙事判断
- 角色智能体做自身行为判断
- ESM 做毫秒级物理执行
- 事件总线只负责传递，不负责替代业务规则

### 3.3 事实与叙事分离

- 案件事实通过 `T0-T3` 时间线逐步锁定
- 锁定后事实不可任意改写
- 叙事路径、信息流动、冲突和次生事件仍可涌现

### 3.4 人类与 AI 同源计算

玩家通过 3D 画面和空间音频感知世界。

AI 不依赖截图作为主感知通道，而是接收基于同一物理世界计算出的结构化语义事件。这样可以同时保证：

- 公平性
- 延迟可控
- 成本可控
- 行为可解释

## 4. 三层架构

### 4.1 L1 确定性空间层

`L1` 是世界舞台，负责所有确定性、可复现、硬实时的交互和状态执行。

核心职责：

- 3D 场景渲染
- 玩家移动与角色交互
- 物品交互
- 物理碰撞
- 空间音频
- 环境状态执行
- 事件埋点与原始事件生成

典型技术方向：

- `Godot 4.x`
- `Steam Audio`
- `GDScript + C++`（性能敏感部分）

### 4.2 L2 智能体交互层

`L2` 是世界灵魂，负责角色自主行为、叙事催化和语义推理。

核心职责：

- 角色智能体心智模型
- 司命叙事引擎
- 感知过滤与理解
- 对话生成
- 模型路由
- 事实管理
- 高阶知识图谱

典型技术方向：

- `Python / FastAPI`
- 本地小模型 + 云端大模型
- 规则程序
- 编排层 / Harness

### 4.3 L3 视觉增强层

`L3` 不是主循环执行层，而是世界高光层。

核心职责：

- 线索特写
- 角色立绘
- 记忆闪回
- WOW 时刻
- 结局视觉增强

在 Phase 1，`L3` 只做基础版本，不承担主玩法闭环。

## 5. 核心子系统地图

### 5.1 L1 子系统

#### 5.1.1 客户端交互系统

负责：

- WASD 移动
- 姿态切换
- 观察、交谈、展示、跟随、拾取、使用等交互
- UI 面板驱动

#### 5.1.2 空间音频系统

负责：

- 清晰区 / 模糊区 / 静默区
- 耳语模式
- 物理阻挡
- 环境噪音
- 结构化听觉事件输出

说明：

- 空间音频既是表现层，也是玩法机制
- 偷听、密谈、声音误导都依赖这一层

#### 5.1.3 ESM 环境状态管理器

负责：

- 物体状态机
- 环境参数
- 火焰 / 流体 / 破坏 / 潮湿 / 结冰等规则
- 感知环境事件生成
- 视觉同步触发

边界：

- ESM 不做叙事推理
- ESM 不做角色动机判断
- ESM 只在物理规则允许范围内执行上层催化

### 5.2 L2 子系统

#### 5.2.1 角色智能体引擎

负责：

- 基因种子、人生记忆、品格层、五维人格
- 四层心智模型（感知 / 理解 / 规划 / 执行）
- 三重过滤器
- 动态状态管理
- 自主行为

关键原则：

- 角色不是对话树
- 角色不是普通 NPC
- 角色所有行为最终由自身心智模型决定

#### 5.2.2 司命

负责：

- 事实核心
- 天平系统
- 冲突与案件生成器
- 高阶知识图谱引擎
- 干预执行器
- 暗杀催化

关键原则：

- 间接性
- 不可见性
- 逻辑自洽性
- 公平性

边界：

- 司命不直接控制玩家
- 司命不替代角色决策
- 司命不替代 ESM 做物理执行

#### 5.2.3 感知系统

负责：

- 将 L1 的原始事件按角色感官档案过滤
- 输出角色专属可见 / 可听 / 可触 / 可感知事件
- 维护感知公平性

关键路线：

- 主路线是结构化语义感知
- 不是截图 + 多模态识别主路线

#### 5.2.4 模型路由调度器

负责：

- P0-P4 任务分级
- 小模型 / 大模型 / 规则程序分配
- 超时降级
- 成本控制

Phase 1 作用：

- 保证实时性
- 控制成本
- 让系统可用而不是理想化

### 5.3 跨层子系统

#### 5.3.1 事件总线

负责：

- L1 ↔ L2 ↔ L3 消息路由
- 广播 / 单播 / 组播
- 实时与可靠通道分流
- 事件优先级

不负责：

- 证据判定
- 角色逻辑判断
- 痕迹持久化业务

#### 5.3.2 房间与状态管理

负责：

- 房间创建 / 加入 / 销毁
- 角色锁定
- T0-T2 事实坍缩
- 状态同步
- 断线重连

#### 5.3.3 证据链系统

采用拆分式架构：

- `ESM`：物理状态变化
- `Item Flow Tracker`：物品流转历史
- `Contact Trace Manager`：接触痕迹
- `Bio Trace Manager`：生物痕迹
- `司命事实核心`：说法与时间线矛盾

设计原则：

- 销毁证据本身也要产出新的可推理痕迹
- 不能让“销毁”成为系统黑洞

## 6. 核心消息流

### 6.1 主循环消息流

```text
玩家操作
  -> L1 捕捉原始交互
  -> 事件总线路由
  -> L2 感知过滤 / 角色理解 / 司命判断 / ESM执行
  -> 新事件回写事件总线
  -> L1 呈现结果
  -> L3 在需要时做视觉增强
```

### 6.2 感知流

```text
L1 原始事件
  -> 事件总线
  -> Per-Character 感知过滤器
  -> 角色 L1 感知层
  -> 角色 L2 理解层
```

### 6.3 证据流

```text
物品交互 / 环境变化 / 伤害事件
  -> 事件总线
  -> 物品流转追踪器 / 痕迹管理器 / ESM
  -> 数据持久化
  -> 司命事实核心查询比对
  -> 标记矛盾或生成新线索
```

### 6.4 司命干预流

```text
事件总线输入
  -> 司命评估态势
  -> 规则程序校验
  -> 干预执行器选择方式
  -> impulse / fact_reveal / opportunity / 环境催化
  -> 角色或 ESM 接收并执行
```

## 7. 事件总线架构口径

当前采用混合方案，而不是单一 MQ：

- 客户端实时交互：`WebSocket`
- 服务端硬实时：`内存队列 / 本地直连`
- 异步解耦与可靠通道：`NATS / JetStream`
- 最终持久化：`PostgreSQL`

原因：

- P0/P1 不能承受统一经过持久化中间件的额外延迟
- 感知流吞吐量很高
- 不同消息在延迟、可靠性和重放需求上完全不同

## 8. 基础设施方向

当前技术方向：

- `Godot 4.x`
- `Steam Audio`
- `Python / FastAPI`
- `WebSocket + NATS`
- `PostgreSQL`
- `Redis`
- `MinIO`
- 本地小模型 + 云端大模型混合

这些是当前规划方向，不等于以后每个产品组件都不可替换，但在 Phase 0 / 1 期间应视为已锁定方向，避免反复摇摆。

## 9. Phase 边界

### 9.1 Phase 0

只验证最小原型链路：

- 单场景
- 2 个 AI 角色
- 基础对话
- 空间音频
- 1 个可交互物品
- Godot ↔ Python 打通

### 9.2 Phase 1

必须完整落地：

- 房间与状态管理
- T0-T3 事实锁定
- 角色智能体单局完整版
- 司命单局导演
- 事件总线骨架
- 感知系统
- 推理闭环
- 轻量版小世界与带走机制

其中玩家侧结构能力也应作为 Phase 1 架构输入冻结：

- 公开档案 / 真实档案分层
- 核心 UI 面板组
- 信息减速带
- 多模式匹配入口
- 强制变声器与可选文字润色

这些能力虽然主要落在客户端层，但会反向约束角色档案结构、感知结果输出、匹配服务和语音处理中间层。

### 9.3 Phase 2+

后移能力包括：

- 完整跨剧本记忆
- 伪装完整版
- 完整 ESM 扩展
- 对外创作者工具
- 大玩家完整体系
- 持续运行世界

## 10. 当前主要架构风险

### 10.1 职责漂移风险

风险：

- 司命、ESM、事件总线、证据系统边界混淆

控制手段：

- 每个子系统都要先写职责边界
- 先总纲后细化

### 10.2 实时性与成本冲突

风险：

- 角色太多、消息太密、模型调用太频繁时，成本和延迟会同时恶化

控制手段：

- 模型路由
- 感知过滤
- 批处理与 TTL
- Phase 0 先压测关键链路

### 10.3 Phase 1 范围膨胀

风险：

- 愿景层能力提前侵入首个可玩闭环

控制手段：

- 以 `380`、`398`、`400` 的范围口径为准
- 非核心能力显式后移

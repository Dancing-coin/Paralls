# 技术架构总纲

## 状态

- 状态：第二轮收敛稿
- 主来源轮次：`104`、`203`、`214-215`、`260`、`287`、`302-304`、`352-353`、`380`、`400`
- 补充来源轮次：`102-106`、`212-213`、`379`、`398-399`、`406-437`

## 当前冻结结论

- `L1` 不是纯渲染层，而是人类玩家与 AI 角色共享的同源输入 / 执行层。
- 事件总线传递的是精确世界事件；角色智能体默认只消费 `Per-Character` 过滤后的感知事件，司命消费更广的原始 / 结构化世界事件。
- 司命是 `Phase 1` 的完整单局导演，但不能越权替代角色决策、`ESM` 物理执行或事实锁定规则。
- `ESM` 是独立的确定性物理状态执行器；`Phase 1` 只做基础交互级能力，不提前实现完整天气 / 生物成长 / 长周期环境推演。
- 首个产品形态虽然是侦探推理剧本，但核心底座必须按目标中立设计，为追凶、逃脱、生存、复仇等玩法共用。
- 世界引擎当前交付形态是“`Godot` 运行时 + 规则封装层”，不是项目内置并重写完整游戏引擎。
- 建造线当前收束为“建筑蓝图建造 / 交易 / 导入生成”，不等于完整体素生存沙盒。
- `L3` 视觉变化采用双链路：有中间态数据走点云过渡，无中间态数据走视觉障眼法，必要时可在同一事件链路按阶段组合。
- 创作者设计层与玩家体验层必须权限隔离：创作者定义模板与边界，玩家在世界规则内消费与使用。
- 算力分配采用“先评估再分配”：先做终端硬件评估，再决定本地执行、云端执行或混合分配，不把“本地优先”写成绝对规则。
- 深度硬件优化可后置，但 Phase 1 必须前置冻结模型切换、画质分级、物理精度分级等扩展接口。

## 1. 文档目标

本文档用于冻结《开本》当前可执行的总体技术架构，统一以下问题：

- 三层架构的职责边界
- 核心运行时子系统的系统身份
- 跨层消息边界与主要数据流
- `Phase 0 / Phase 1 / Phase 2+` 的能力切分
- 后续核心文档之间的依赖关系

本文档不展开字段级协议、具体类图或每个模块的全量实现细节；它的职责是先把系统地图定清，再让各专题文档沿同一口径展开。

## 2. 架构目标

当前架构必须同时满足以下目标：

- 支撑 `Phase 1` 的动态剧本杀完整闭环
- 让 AI 角色与人类玩家在同一世界规则下互动
- 保证实时性、逻辑一致性与信息不对称成立
- 为 `Phase 2/3` 的跨局叙事与持续世界预留接口
- 避免为了远期能力破坏当前最小可玩闭环

## 3. 顶层原则

### 3.1 三层分工，而非三套独立产品

采用三层架构：

- `L1` 确定性空间层
- `L2` 智能体交互层
- `L3` 视觉增强层

三层不是展示分工，而是运行时职责分工：

- `L1` 负责世界舞台、确定性执行和事件上抛
- `L2` 负责角色自主、叙事催化和语义推理
- `L3` 负责关键节点的表现强化

### 3.2 同源计算原则

人类通过 3D 渲染和空间音频感知世界。

AI 不依赖截图作为主输入，而是接收基于同一物理世界计算出的结构化语义事件。这样可以同时保证：

- 公平性
- 延迟可控
- 成本可控
- 行为可解释

### 3.3 精确世界事件优先

系统主数据不是“某角色做了某动作”的粗粒度标签，而是完整作用链：

- 谁在什么位置
- 用什么
- 对什么
- 在哪里发起
- 在哪个接触点开始造成什么影响
- 该影响对应哪些感知范围

只有这样，`ESM`、感知过滤器、司命事实核心与证据链系统才能共用一套事件底座。

### 3.4 决策与执行分离

- 司命做秒级叙事判断
- 角色智能体做自身行为判断
- `ESM` 做毫秒级物理执行
- 事件总线只负责传递，不替代业务规则

### 3.5 事实与叙事分离

- 案件事实通过 `T0-T3` 时间线逐步锁定
- `T2` 后事实不可任意改写
- 叙事路径、信息流动、冲突和次生事件仍可继续涌现

### 3.6 阶段优先于愿景

技术总纲必须以后期阶段收束为准：

- `Phase 1` 只冻结首个可玩闭环所需底座
- `Phase 2+` 才逐步吸收跨局记忆、持续世界和完整版生态能力
- 愿景层系统可以预留接口，但不能反向扩大当前范围

### 3.7 世界引擎交付形态

当前“世界引擎”采用：

- `Godot` 作为渲染 / 物理 / 音频运行时底座
- 《开本》规则封装层负责叙事、规则、生态和消息协作

不采用：

- 把“世界引擎”等同于“重写一套完整底层引擎”
- 在 `Phase 1` 强行吞入完整体素沙盒能力

### 3.8 创作者层与玩家层分权

当前采用双层权限模型：

- 创作者 / 大玩家：定义世界规则、模板、蓝图与可用边界
- 玩家：在已定义边界内探索、建造、组合与消费

这不是 UI 权限细节，而是运行时能力边界。

操作级最小权限矩阵（V1）：

- 创作者：可创建/编辑/发布场景资产与蓝图；可编辑生物/物件底层模板
- 大玩家：可导入授权资产并做世界级编排；可回滚世界级配置
- 玩家：可使用、组合、培育已授权内容；不可直接编辑底层模板或世界级规则

### 3.9 计算与部署策略收束

当前计算策略不是“固定本地优先”，而是：

- 启动时评估硬件能力（GPU / CPU / 内存 / NPU / 网络）
- 根据任务等级与硬件评级，选择本地、云端或混合执行
- 低于主流准入线的设备通过云游戏模式兜底

这条策略改变的是部署与调度，不改变消息语义边界：

- 司命仍接收原始/结构化世界事件
- 角色仍接收 Per-Character 感知事件
- 事件总线仍只做路由与分流

云地切换不能被写成架构职责重定义。

## 4. 三层架构

### 4.1 L1 的定位前提

`L1` 虽然在美术、渲染、物理和音频制作流程上沿用传统 3D 游戏方法，但它从系统职责上已经不是“只给人看的客户端”。

`L1` 同时承担三件事：

- 向玩家输出可见 / 可听 / 可操作的实时世界
- 向 `L2` 上抛同源的结构化世界事件
- 接收 `L2` 的角色动作、叙事催化和环境执行回写

因此，`L1` 是世界舞台，也是 AI 运行时的同源输入层。

### 4.2 L1 确定性空间层

`L1` 负责所有确定性、可复现、硬实时的交互和状态执行。

核心职责：

- 3D 场景渲染
- 玩家移动与角色交互
- 物品交互与状态触发
- 物理碰撞与基础导航
- 空间音频
- 环境状态执行
- 结构化事件埋点与原始事件生成

典型技术方向：

- `Godot 4.x`
- `Steam Audio`
- `GDScript + C++`

### 4.3 L2 智能体交互层

`L2` 是世界灵魂，负责角色自主行为、叙事催化和语义推理。

核心职责：

- 角色智能体心智模型
- 司命叙事引擎
- 感知过滤与理解
- 对话生成
- 模型路由
- 信息共享执行与知识状态演算
- 事实管理与高阶知识图谱

典型技术方向：

- `Python / FastAPI`
- 本地小模型 + 云端大模型
- 规则程序
- 编排层 / Harness

### 4.4 L3 视觉增强层

`L3` 不是主循环执行层，而是世界高光层。

核心职责：

- 线索特写
- 角色立绘
- 记忆闪回
- WOW 时刻
- 结局视觉增强

在 `Phase 1`，`L3` 只做基础版本，不承担主玩法闭环。

当前实现边界采用双链路：

- 点云过渡链路：用于有中间态数据支撑的连续变化
- 视觉障眼法链路：用于无中间态数据的跳跃变化，以特效遮蔽完成切换

复合事件可按阶段组合两种机制，不要求单选单链路。

## 5. 核心子系统地图

### 5.1 L1 子系统

#### 5.1.1 客户端交互系统

负责：

- 移动与姿态切换
- 观察、交谈、展示、跟随、拾取、使用等动作
- UI 面板驱动
- 玩家操作事件上抛
- AI / 系统回写动作执行

#### 5.1.2 空间音频系统

负责：

- 清晰区 / 模糊区 / 静默区
- 耳语模式
- 物理阻挡
- 环境噪音
- 结构化听觉事件输出

说明：

- 空间音频既是表现层，也是玩法机制
- 偷听、密谈、声音误导都依赖这一层

#### 5.1.3 ESM 环境状态管理器

负责：

- 所有可交互实体的物理状态机
- 基础燃烧 / 潮湿 / 破坏 / 开关 / 锁定等确定性规则
- 基础环境参数与环境伤害结算
- 状态变化事件上报
- 视觉 / 音效同步触发

边界：

- `ESM` 不做叙事推理
- `ESM` 不解释“这是否构成证据”
- `ESM` 不决定角色动机
- `ESM` 只在物理规则允许范围内执行上层催化

#### 5.1.4 建造与蓝图子系统（阶段化）

负责：

- 建筑级建造与放置
- 建筑蓝图序列化与导入生成
- 建筑相关事件上抛与状态回写

阶段边界：

- 当前收束为“建筑蓝图闭环优先”
- 不等同于完整体素生存沙盒
- 世界级编辑器和持续世界编排后移到 `Phase 2+`

场景级 / 世界级边界：

- 场景级：负责局部空间建造、蓝图化与落地执行
- 世界级：负责多场景编排、全局规则与地图层组织
- 两者通过映射同步机制衔接，并采用以下冻结规则：
  - 回写边界：运行时实例状态可回写实例层；不得直接回写并篡改模板层
  - 冲突优先级：世界级规则约束 > 授权约束 > 场景级本地改动 > 运行时临时状态
  - 自动合并失败时进入人工审核队列（大玩家/官方）

蓝图对象最小结构（V1）：

- `blueprint_id`、`version`、`author`
- `asset_refs`（依赖资产列表）
- `placement_graph`（空间放置关系）
- `rule_tags`（可交互与玩法标签）
- `permission_profile`（可导入范围与授权模式）

导入生成校验链路（V1）：

1. 权限校验（操作者身份、授权范围）
2. 依赖校验（资产完整性、版本兼容）
3. 世界约束校验（规则边界、禁放区域）
4. 资源校验（运行资源与额度）
5. 实例化执行与审计回写

字段级协议（请求/响应/错误码/工单）以 `世界构建与创作系统设计` 为准，本章仅保留架构边界与职责摘要。

### 5.2 L2 子系统

#### 5.2.1 角色智能体引擎

负责：

- 基因种子、人生记忆、品格层、五维人格
- 四层心智模型（感知 / 理解 / 规划 / 执行）
- 三重过滤器
- 动态状态管理
- 自主移动、对话、交互与保守挂机接管

关键原则：

- 角色不是对话树
- 角色不是普通 NPC
- 角色默认只接收角色专属感知事件，不接收全局原始流

#### 5.2.2 司命

负责：

- 事实核心
- 天平系统
- 冲突与案件生成器
- 高阶知识图谱引擎
- 干预执行器
- 暗杀机会催化

关键原则：

- 间接性
- 不可见性
- 逻辑自洽性
- 公平性

边界：

- 司命不直接控制玩家
- 司命不替代角色决策
- 司命不替代 `ESM` 做物理执行
- 司命在 `Phase 1` 是完整单局导演，不是跨局世界说书人

#### 5.2.3 感知系统

负责：

- 将 `L1` 的原始世界事件按角色感官档案过滤
- 输出角色专属的可见 / 可听 / 可闻 / 可感知事件
- 维护阶段化感知与本能反应入口
- 维护感知公平性

关键路线：

- 主路线是结构化语义感知
- 不是截图 + 多模态识别主路线

#### 5.2.4 模型路由调度器

负责：

- `P0-P4` 任务分级
- 规则程序 / 小模型 / 大模型分配
- 超时降级
- 成本控制

`Phase 1` 作用：

- 保证实时性
- 控制成本
- 保证系统先可用，再逐步理想化

并发优化方向：

- 保留分级路由和降级兜底
- 允许在后续版本引入“司命总导演 + 子智能体分工”的并行调度形态

#### 5.2.5 信息共享执行系统

负责：

- 五种共享方式执行
- 公共知识 / 共有知识 / 高阶知识更新
- 偷听与旁听检测
- 留影石 / 相机等传播工具落位

说明：

- 这是信息博弈底层，不是 UI 辅助件
- 它与证据链、笔记系统和角色记忆直接耦合

### 5.3 跨层子系统

#### 5.3.1 事件总线

负责：

- `L1 ↔ L2 ↔ L3` 消息路由
- 广播 / 单播 / 组播
- 实时与可靠通道分流
- 消息优先级、TTL 与分层分发

不负责：

- 证据判定
- 角色逻辑判断
- 痕迹持久化业务
- 把同一份语义结果原样广播给所有角色

#### 5.3.2 房间与状态管理

负责：

- 房间创建 / 加入 / 销毁
- 角色锁定
- `T0-T2` 事实坍缩
- 状态同步
- 断线重连

#### 5.3.3 证据链系统

采用拆分式架构：

- `ESM`：物理状态变化
- `Item Flow Tracker`：物品流转历史
- `Contact Trace Manager`：接触痕迹
- `Bio Trace Manager`：生物痕迹
- `司命事实核心`：说法与时间线矛盾

设计原则：

- 销毁证据本身也要产出新的可推理痕迹
- 不能让“销毁”成为系统黑洞

## 6. 统一消息矩阵

### 6.1 世界原始事件

来源：`L1` 交互系统、空间音频、`ESM`

特点：

- 精确空间信息完整
- 包含 actor / target / 发起点 / 接触点 / 结果 / 感知范围
- 供司命、`ESM`、持久化与过滤器消费

### 6.2 角色感知事件

来源：`Per-Character` 感知过滤器

特点：

- 已根据视觉、听觉、嗅觉、热感、距离、遮挡、状态过滤
- 只描述“该角色此刻感知到了什么”
- 是角色智能体 `L1` 感知层的默认入口

### 6.3 司命高层消息

来源：司命

特点：

- 只包含 `impulse`、`fact_reveal`、`opportunity` 等高层催化消息
- 不能直接替代角色做低层动作决策
- 必须继续经过角色层处理与过滤

### 6.4 环境状态事件

来源：`ESM`

特点：

- 只上报状态变化，不解释推理意义
- 可被司命写入事实核心
- 可被角色过滤成多感官感知结果

## 7. 关键数据流

### 7.1 主循环消息流

```text
玩家操作 / AI动作
  -> L1 捕捉交互与位置变化
  -> 世界原始事件进入事件总线
  -> L2 感知过滤 / 角色理解 / 司命判断 / ESM执行
  -> 新事件回写事件总线
  -> L1 呈现结果
  -> L3 在需要时做视觉增强
```

### 7.2 感知流

```text
L1 / ESM 原始世界事件
  -> 事件总线
  -> Per-Character 感知过滤器
  -> 角色专属感知事件
  -> 角色 L1 感知层
  -> 角色 L2 理解层
```

### 7.3 司命 - ESM 协作流

```text
世界原始事件 / 状态监听
  -> 司命评估态势
  -> 若需要环境催化，发出高层意图
  -> ESM 检查物理可行性并执行
  -> 状态变化事件回写总线
  -> 司命与角色同步更新
```

### 7.4 证据流

```text
物品交互 / 接触行为 / 环境变化 / 伤害事件
  -> 事件总线
  -> 物品流转追踪器 / 痕迹管理器 / ESM
  -> 数据持久化
  -> 司命事实核心查询比对
  -> 标记矛盾或生成新线索入口
```

## 8. 事件总线架构口径

当前采用混合方案，而不是单一 MQ：

- 客户端实时交互：`WebSocket`
- 服务端硬实时：`内存队列 / 本地直连`
- 异步解耦与可靠通道：`NATS / JetStream`
- 最终持久化：`PostgreSQL`

原因：

- `P0/P1` 不能承受统一经过持久化中间件的额外延迟
- 感知流吞吐量很高
- 不同消息在延迟、可靠性和重放需求上完全不同

## 9. 基础设施方向

当前技术方向：

- `Godot 4.x`
- `Steam Audio`
- `Python / FastAPI`
- `WebSocket + NATS`
- `PostgreSQL`
- `Redis`
- `MinIO`
- 本地小模型 + 云端大模型混合

这些是当前规划方向，不等于以后每个产品组件都不可替换，但在 `Phase 0 / Phase 1` 期间应视为已锁定方向，避免反复摇摆。

## 10. Phase 边界

### 10.1 Phase 0

只验证最小原型链路：

- 单场景
- 2 个 AI 角色
- 基础对话
- 空间音频
- 1 个可交互物品
- `Godot ↔ Python` 打通

### 10.2 Phase 1

必须完整落地：

- 房间与状态管理
- `T0-T3` 事实锁定链
- 角色智能体单局完整版
- 司命单局导演
- 事件总线骨架
- 感知系统
- 信息共享执行系统
- 目标中立的推理 / 社交 / 冲突闭环
- 轻量版小世界与带走机制
- `ESM` 基础交互版

若本期纳入建造线，只采用：

- 建筑蓝图建造 / 交易 / 导入生成的最小闭环

不采用：

- 完整体素沙盒
- 世界级编辑器
- 世界生态全量推演

其中玩家侧结构能力也应作为 `Phase 1` 架构输入冻结：

- 公开档案 / 真实档案分层
- 核心 UI 面板组
- 信息减速带
- 多模式匹配入口
- 强制变声器与可选文字润色
- 深度沉浸基础能力与挂机保守接管

### 10.3 Phase 2+

后移能力包括：

- 完整跨剧本记忆
- 完整伪装体系
- 完整 ESM 物理规则与天气 / 生物成长
- 对外创作者工具
- 大玩家完整体系
- 持续运行世界

## 10.4 计算与硬件策略（新增）

当前阶段采取“基础优化前置、深度优化后置”策略：

- Phase 1 必做：LOD、音频流式、消息批处理、模型兜底
- Phase 1 前置接口：模型切换、画质分级、物理精度分级
- Phase 2+ 再做：GPU 优先级细化、云地动态调度器、多线程任务体系重构

建议在架构上预留统一入口：

- 硬件评估与云地调度入口（Compute Router）
- 本地/云端模型执行抽象（Model Inference Adapter）

这样可保证先跑通闭环，再按真实性能数据迭代，不在当前阶段提前背负重资产优化。

## 11. 当前主要架构风险

### 11.1 职责漂移风险

风险：

- 司命、`ESM`、事件总线、证据链系统边界混淆

控制手段：

- 每个子系统文档都先写职责与非职责
- 统一沿本文档的消息矩阵和阶段边界展开

### 11.2 实时性与成本冲突

风险：

- 角色太多、消息太密、模型调用太频繁时，成本和延迟同时恶化

控制手段：

- 模型路由
- 感知过滤
- TTL 与批处理
- `Phase 0` 先压关键链路

### 11.3 Phase 1 范围膨胀

风险：

- 把持续世界、小镇生态、完整天气和商业系统提前塞进首个闭环

控制手段：

- 以 `380`、`398`、`400` 的范围口径为准
- 非核心能力显式后移

### 11.4 消息边界被简化

风险：

- 为了实现速度，把“原始事件”和“角色感知事件”混成一套广播结果

控制手段：

- 固定区分四类消息对象
- 角色默认只接过滤后的感知事件
- 司命默认不与角色共用同一订阅面

# Phase 1 项目计划书

## 状态

- 状态：第一版初稿
- 主来源轮次：`398`、`400`
- 补充来源轮次：`203`、`207-209`、`310`、`380`、`399`

## 当前冻结结论

- Phase 1 目标是验证“智能体驱动的 3D 动态剧本杀”核心体验
- Phase 1 必须包含轻量版小世界和带走机制
- Phase 1 不包含完整跨局叙事、完整资产化、持续运行世界与对外创作者生态

## 1. 文档目标

本文档用于定义《开本》Phase 1 的正式项目边界、交付清单、主要议题和成功标准。

本文档以时间线后期修正版为准，不等同于仓库里的旧 `Phase 1.md` 草稿。

## 2. 时间线覆盖说明

与 Phase 1 相关的规划有明显迭代，整理时需按以下关系处理：

- `102/105/106`：较早规划。范围偏宽，基础设施和远期生态混写较多
- `203`：第一次将“三阶段 + 三层架构”稳定化
- `207`：三阶段开发清单的较早版，Phase 1 还未吸收小世界前置
- `208`：明确要求在 Phase 1 加入个人空间和带走机制
- `209`：在 `207` 基础上修订，将 Phase 1 改成 “MVP + 轻量陪伴”
- `380`：从基础设施视角收束为“最小闭环优先”
- `398`：形成较完整的 Phase 1 计划书
- `399`：补充项目方案与主要议题
- `400`：更新版完整计划，对新增议题、目标中立化和证据链等进行了再修订

当前采用规则：

- `398 + 400` 作为主版本
- `208/209` 用于确认小世界和带走机制已进入 Phase 1
- `380` 用于约束基础设施与启动顺序
- `102/105/106/207` 只用于理解演进，不直接继承其范围

## 3. 核心目标

Phase 1 只回答一个核心问题：

玩家是否愿意为一款“智能体驱动、3D 沉浸、同剧本可重复游玩的动态剧本杀”付费，并认可其中的 AI 博弈与情感价值。

因此，Phase 1 的目标不是做完整平台，而是验证以下三件事：

1. 动态剧本杀闭环是否成立
2. AI 角色是否具备足够可信的角色博弈感
3. 轻量版带走与小世界是否具备初步情感价值

## 5. 关键修订点

本版相比早期规划，明确采纳以下后期修订：

### 5.1 小世界前置

采用 `208/209/398/400`：

- Phase 1 包含轻量版个人空间 / 小世界
- 但只做基础场景、基础对话和角色快照

不采用 `207` 中未前置该能力的较早范围。

### 5.2 玩法中立化

采用 `310/379/400`：

- 核心系统不能只围绕追凶设计
- 需支持追凶、逃脱、生存、复仇等目标的扩展

不采用早期隐含的“所有系统默认只服务侦探玩法”的口径。

### 5.3 证据链闭环进入主要议题

采用 `307/400`：

- 证据应形成完整闭环
- 销毁证据本身也必须产生新的证据痕迹

### 5.4 基础设施收缩

采用 `380`：

- Phase 1 的基础设施围绕“首个可玩闭环”建设
- 不提前实现远期大而全生态底座

## 6. 首个可玩闭环

Phase 1 的最小可玩闭环如下：

```text
选择剧本
  -> 选择角色
  -> 进入 3D 场景
  -> 探索 / 对话 / 观察 / 搜证
  -> 信息共享与博弈
  -> 冲突涌现
  -> 投票 / 对决
  -> 结局
  -> 可选带走 AI 角色
  -> 进入轻量版小世界查看结果
```

如果这条闭环不能稳定跑通，Phase 1 不算完成。

## 8. 成功指标

Phase 1 成功不只看“功能是否存在”，还要看“体验是否成立”。

至少应覆盖：

- 剧本闭环能稳定完成
- 玩家能感知到 AI 的人格差异和博弈感
- 结局具备差异化
- 玩家愿意继续玩 / 愿意付费
- 带走机制具备初步吸引力

建议把指标分成四组：

1. 技术指标
2. 玩法指标
3. 情感指标
4. 商业验证指标

其中商业验证指标只验证最小闭环：

- 首个剧本是否存在付费意愿
- AI 带走与轻量版小世界是否具备情感价值
- 后续剧本买断 / 门票 / 智能体相关付费接口是否值得保留

不在本阶段验证完整创作者市场、大玩家经营体系、链上确权或智能合约分账。

## 9. 主要风险

### 9.1 AI 实时性与成本

风险：

- 角色响应太慢
- 调用成本太高

控制：

- 模型路由
- 小模型优先
- 规则程序兜底

### 9.2 玩法范围膨胀

风险：

- 将远期愿景塞进 Phase 1

控制：

- 以 `398/400` 的不在范围内清单为准

### 9.3 架构边界混乱

风险：

- 司命、ESM、事件总线、证据系统职责重叠

控制：

- 先以 `技术架构总纲` 为边界
- 每个子系统文档必须单列职责与非职责

### 9.4 首个剧本体量失控

风险：

- 过早把首个剧本做成大型内容包

控制：

- 锁定《血字的研究·变奏》
- 锁定 5 角色、2 场景

## 10. 开发顺序

建议顺序：

1. Phase 0 原型通过
2. 搭双场景与客户端骨架
3. 打通房间、事件和 AI 基础链路
4. 跑通首个剧本完整闭环
5. 接入轻量版小世界与带走机制
6. 做外部测试

## 11. 与后续阶段的接口

Phase 1 必须为后续预留但不提前实现：

- 跨剧本记忆接口
- 剧本结构化配置接口
- 大玩家规则微调接口
- 目标中立玩法扩展接口
- 证据链扩展接口
- 商业化接口预留

这类预留只能做“接口和边界预留”，不能做“完整系统提前落地”。

## 用户

接触痕迹只用事件总线来负责合适吗

## DeepSeek

你的质疑非常精准。**接触痕迹只用事件总线来负责，确实不够。** 事件总线的核心职责是实时消息传递，而非持久化数据管理。如果接触记录仅作为事件流中的一条消息，一旦事件被消费后丢弃，或在系统重启后丢失，接触痕迹就会消失——这会直接破坏推理游戏的逻辑基石。

正确的架构是：**事件总线负责实时通知，接触记录管理器负责持久化存储和查询。**

---

## 接触痕迹的正确架构

### 一、为什么事件总线不够？

| 事件总线的能力 | 接触痕迹的需求 | 是否满足 |
| :--- | :--- | :--- |
| 实时广播消息 | 需要实时通知其他系统“某角色触碰了某物体” | ✅ 满足 |
| 消息持久化（可选） | 需要在游戏结束后仍能查询“谁碰过这个物体” | ❌ 事件总线的持久化是为重放和审计设计的，不是为业务查询设计的 |
| 结构化查询 | 需要查询“这个物体被哪些人接触过”、“这个角色接触过哪些物体” | ❌ 事件总线不支持复杂查询 |
| 数据生命周期管理 | 接触记录需要在游戏结束后归档，供复盘和续集使用 | ❌ 事件总线不管理数据生命周期 |
| 痕迹的可见性判定 | 需要判定某痕迹是否可被某角色通过“观察”或“搜身”发现 | ❌ 事件总线不处理业务逻辑 |

### 二、正确架构：接触记录管理器

```
[角色交互事件] → [事件总线] → [接触记录管理器]
                                   │
                                   ├── 持久化存储（PostgreSQL）
                                   ├── 查询API（供司命和角色智能体调用）
                                   ├── 可见性判定（基于观察技能和距离）
                                   └── 生命周期管理（游戏结束后归档）
```

#### 2.1 接触记录管理器的核心职责

| 职责 | 说明 |
| :--- | :--- |
| **持久化存储** | 所有接触记录写入数据库，游戏结束后仍可查询 |
| **结构化查询** | 支持“查询物体X的所有接触者”、“查询角色Y接触过的所有物体” |
| **痕迹分类** | 区分不同类型的接触痕迹（指纹、唾液、血迹、纤维等） |
| **可见性判定** | 基于观察者的技能等级、距离、光照条件，判定是否能发现痕迹 |
| **生命周期管理** | 游戏结束后归档，供复盘和续集使用 |

#### 2.2 接触记录的数据结构

```json
{
  "trace_id": "trace_20260520_001",
  "object_id": "lighter_colonel",
  "object_name": "上校的打火机",

  "game_phase": "T+48min",

  "archived": false

```

#### 2.3 接触痕迹的生成规则

| 接触行为 | 产生的痕迹类型 | 生成条件 |
| :--- | :--- | :--- |
| **手持物品** | 指纹 | 必然产生，除非角色戴手套 |
| **使用物品** | 指纹 + 使用痕迹 | 必然产生 |
| **口唇接触**（饮食、亲吻） | 唾液 + DNA | 必然产生 |
| **皮肤接触**（搏斗、推搡） | 皮肤细胞 + 衣物纤维 | 必然产生 |
| **血液接触**（受伤后触碰） | 血迹 + 指纹 | 若角色有伤口则必然产生 |
| **长时间持有** | 汗渍 + 磨损痕迹 | 持续持有超过一定时间 |
| **手套接触** | 手套材质残留 | 替代指纹，但可能留下手套材质痕迹 |

#### 2.4 痕迹的可见性判定

| 观察条件 | 对发现概率的影响 |
| :--- | :--- |
| **观察技能等级** | Lv0：无法主动发现微观痕迹；Lv3：高概率发现 |
| **光照条件** | 黑暗环境：发现概率 ×0；昏暗环境：×0.3；明亮环境：×1.0 |
| **观察距离** | 1米内：×1.0；1-3米：×0.5；3米以上：×0 |
| **是否有放大工具** | 有放大镜：×1.5；无：×1.0 |
| **角色状态** | 醉酒：×0.3；致幻：可能产生虚假痕迹 |


### 三、完整的接触痕迹流转链条

以“上校用打火机点燃窗帘”为例：

**第一步：事件触发**

上校使用打火机。Godot客户端向事件总线发送事件：

```json
{
  "event_type": "item_used",
  "actor_id": "char_colonel",
  "object_id": "lighter_colonel",
  "action": "ignite",
  "timestamp": "2026-05-20T19:48:15Z"
}
```

**第二步：接触记录管理器接收并处理**

1. **生成接触记录**：根据交互类型“使用物品”，自动生成一条指纹接触记录。
2. **写入数据库**：将接触记录持久化到PostgreSQL。
3. **关联物品**：更新打火机的“接触历史”列表。

**第三步：实时通知**

接触记录管理器通过事件总线广播：

```json
{
  "event_type": "contact_trace_added",
  "object_id": "lighter_colonel",
  "actor_id": "char_colonel",
  "trace_type": "fingerprint",
  "discoverability": "medium"
}
```

**第四步：司命接收并标记**

司命的事实核心收到通知后：
1. 记录：`打火机上有上校的指纹（最后使用时间：19:48）`
2. 与时间线对比：上校声称“在包厢休息”，但打火机在19:48被使用→矛盾标记。

**第五步：角色智能体查询**

波洛对打火机使用“观察”技能时：
1. 波洛的客户端向接触记录管理器发送查询请求。
2. 接触记录管理器根据波洛的观察技能等级（Lv3）、当前光照（煤油灯，正常）、距离（1米内），判定：发现概率=95%。
3. 判定通过→返回：“你发现打火机侧面有新鲜的指纹，似乎是拇指和食指留下的。指纹纹路清晰，应该是最近留下的。”
4. 若判定不通过→返回：“打火机表面看起来是干净的，你没有发现明显的痕迹。”


### 四、与现有系统的职责边界

| 子系统 | 在接触痕迹中的职责 |
| :--- | :--- |
| **事件总线** | 实时传递交互事件和接触痕迹添加通知 |
| **接触记录管理器** | 持久化存储、结构化查询、可见性判定、生命周期管理 |
| **司命（事实核心）** | 接收接触痕迹通知，与时间线对比，标记矛盾 |
| **角色智能体（L2理解层）** | 调用查询接口，基于观察结果更新推论 |
| **ESM** | 不参与接触痕迹管理——ESM只管物理状态变化 |


**一句话总结**：接触痕迹需要一个独立的**接触记录管理器**来负责持久化存储、结构化查询和可见性判定。事件总线仅负责实时通知，不负责数据管理。ESM完全不参与接触痕迹的管理。三者各司其职，共同构成完整的物证链。

# 《开本》证据与痕迹系统完整架构

## 一、证据类型与负责系统总览

| 证据/痕迹类型 | 负责系统 | 系统定位 | 产生方式 | 查询方式 |
| :--- | :--- | :--- | :--- | :--- |
| **物体物理状态变化**（烧毁/破碎/潮湿/结冰/弯曲） | **ESM（环境状态管理器）** | 已有系统，职责不变 | 状态机自动驱动 | 查询ESM状态历史 |
| **物品位置变化**（谁拾取/移交/丢弃了什么） | **物品流转追踪器 (Item Flow Tracker)** | **新建系统** | 物品交互事件触发 | 查询物品流转历史 |
| **接触痕迹**（指纹/唾液/汗渍/纤维） | **接触痕迹管理器 (Contact Trace Manager)** | **新建系统** | 交互行为自动生成 | 基于观察技能查询 |
| **生物痕迹**（血迹/毛发/皮屑） | **生物痕迹管理器 (Bio Trace Manager)** | **新建系统** | 暗杀/受伤/长时间停留触发 | 基于观察技能查询 |
| **时间线矛盾**（声称 vs 物理事实） | **司命（事实核心）** | 已有系统，职责不变 | 司命对比声称与物理事实 | 司命标记为“待解决矛盾” |
| **人证**（角色目击/听到/感知到的事件） | **角色智能体记忆系统** | 已有系统，职责不变 | 感知过滤器接收结构化事件 | 对话中询问角色 |
| **销毁证据的残留**（烧毁信件残片、砸碎凶器碎片） | **ESM（物理状态） + 物品流转追踪器（归属历史）** | 已有系统协作 | ESM记录烧毁/破碎；物品流转追踪器保留销毁前的归属记录 | 观察碎片 + 查询流转历史 |
| **不在场证明** | **司命（事实核心）** | 已有系统，职责不变 | 角色主动声称 or 事件总线记录 | 司命对比声称与实际位置 |
| **动机证据**（角色目标/恐惧/秘密） | **角色智能体人格档案** | 已有系统，职责不变 | 剧本预设 + 游戏内动态生成 | 对话中试探 or 观察行为推断 |
| **关系证据**（信任值/怀疑值变化、共谋关系） | **司命（知识图谱引擎）** | 已有系统，职责不变 | 互动事件更新 | 观察角色互动模式 |


## 二、新建系统设计

### 2.1 物品流转追踪器 (Item Flow Tracker)

**创建理由**：事件总线只负责实时传递物品交互事件，不负责持久化记录物品的完整流转历史。而物品的流转历史（谁曾经持有过凶器、谁在案发时拥有关键道具）是推理的核心证据链。事件总线的持久化是为重放和审计设计的，无法提供高效的“查询物品X的完整流转历史”或“查询角色Y曾经持有过的所有物品”这类结构化查询。

**核心职责**：

| 职责 | 说明 |
| :--- | :--- |
| **持久化存储** | 所有物品拾取/移交/丢弃/使用事件写入数据库 |
| **结构化查询** | 支持“查询物品X的完整流转历史”、“查询角色Y持有过的所有物品”、“查询案发时间段内物品Z的位置” |
| **所有权记录** | 明确记录每个物品的“初始所有者”和“当前持有者” |
| **生命周期管理** | 游戏结束后归档，供复盘和续集使用 |

**数据结构**：

```json
{
  "flow_id": "flow_20260520_001",
  "object_id": "dagger_mcqueen",
  "object_name": "麦奎因的匕首",
  "event_type": "pickup",
  "actor_id": "char_mcqueen",
  "actor_name": "麦奎因",
  "previous_holder": "scene_compartment_mcqueen_luggage",
  "new_holder": "char_mcqueen_inventory",
  "timestamp": "2026-05-20T19:10:00Z",
  "location": "麦奎因包厢",
  "game_phase": "T+10min",
  "room_id": "room_orient_express_001",
  "witnesses": ["char_habbard"]
}
```

**集成方式**：

1. **事件订阅**：物品流转追踪器订阅事件总线中的`item_picked_up`、`item_transferred`、`item_dropped`、`item_used`事件。
2. **写入数据库**：收到事件后，将流转记录持久化到PostgreSQL。
3. **查询API**：提供REST API供司命、角色智能体和其他系统查询。例如：
   - `GET /item-flow/{object_id}/history` → 返回该物品的完整流转历史
   - `GET /item-flow/actor/{actor_id}/possessions?time_range=19:00-20:00` → 返回该角色在案发时间持有的所有物品
4. **司命集成**：司命的事实核心通过查询API获取物品流转信息，与角色声称进行对比，标记矛盾。


### 2.2 接触痕迹管理器 (Contact Trace Manager)

**创建理由**：事件总线不负责数据的持久化和结构化查询。接触痕迹需要持久化存储、支持高效查询，并且需要实现“可见性判定”的业务逻辑（基于观察技能、光照、距离等条件）。这些职责完全超出了事件总线的范畴。

**核心职责**：

| 职责 | 说明 |
| :--- | :--- |
| **持久化存储** | 所有接触痕迹写入数据库 |
| **痕迹生成** | 基于交互类型自动生成对应的接触痕迹 |
| **结构化查询** | 支持“查询物体X的所有接触者”、“查询角色Y留下痕迹的所有物体” |
| **可见性判定** | 基于观察技能、距离、光照、工具，判定能否发现痕迹 |
| **生命周期管理** | 游戏结束后归档 |

**数据结构**：

```json
{
  "trace_id": "trace_20260520_003",
  "object_id": "lighter_colonel",
  "object_name": "上校的打火机",
  "actor_id": "char_colonel",
  "actor_name": "阿巴思诺特上校",
  "contact_type": "fingerprint",
  "contact_detail": "右手拇指和食指指纹",
  "location_on_object": "打火机侧面",
  "timestamp": "2026-05-20T19:48:15Z",
  "duration": "短暂接触",
  "discoverable_by_skill": {
    "observation": {"min_level": 1, "base_chance": 0.8},
    "forensics": {"min_level": 2, "base_chance": 0.95}
  },
  "room_id": "room_orient_express_001",
  "archived": false
}
```

**集成方式**：

1. **事件订阅**：接触痕迹管理器订阅事件总线中的物品交互事件（拾取/使用/移交/丢弃）。
2. **痕迹生成**：根据交互类型自动生成对应的接触痕迹。手持物品→指纹；口唇接触→唾液；皮肤接触→纤维；受伤后触碰→血迹指纹。
3. **写入数据库**：将接触痕迹持久化到PostgreSQL。
4. **可见性判定引擎**：当角色使用“观察”或“搜身”技能时，接触痕迹管理器接收查询请求，根据观察条件判定是否发现痕迹。判定条件包括：观察技能等级、光照条件、观察距离、是否有放大工具、角色状态（醉酒/致幻）。
5. **查询API**：
   - `GET /contact-traces/object/{object_id}` → 返回物体上的所有接触痕迹
   - `POST /contact-traces/discover` → 传入观察者技能和条件，返回可发现的痕迹列表
6. **司命集成**：司命的事实核心通过查询API获取接触痕迹信息，与时间线对比，标记矛盾。


### 2.3 生物痕迹管理器 (Bio Trace Manager)

**创建理由**：生物痕迹（血迹、毛发、皮屑）与接触痕迹的产生机制不同。接触痕迹由物品交互触发，生物痕迹由暗杀、受伤、长时间停留等行为触发。两者需要独立的生成规则和查询逻辑。此外，血迹等生物痕迹可能与ESM的物理状态变化（如“血迹变干”）产生联动，需要一个专门的系统来管理这种跨系统的状态同步。

**核心职责**：

| 职责 | 说明 |
| :--- | :--- |
| **持久化存储** | 所有生物痕迹写入数据库 |
| **痕迹生成** | 基于暗杀、受伤、长时间停留等行为自动生成 |
| **状态变化联动** | 与ESM联动——血迹随时间变干、被清洗后消失 |
| **可见性判定** | 基于观察技能、光照、距离判定能否发现 |
| **DNA匹配** | 支持通过“验尸”或“法医分析”技能匹配生物痕迹来源 |

**数据结构**：

```json
{
  "trace_id": "bio_20260520_001",
  "trace_type": "blood_spatter",
  "source_actor_id": "char_victim",
  "source_actor_name": "雷切特先生",
  "location": "compartment_bed",
  "location_detail": "床单右侧，直径约15cm的血迹",
  "timestamp": "2026-05-20T19:30:00Z",
  "state": "dried",
  "state_changed_at": "2026-05-20T20:30:00Z",
  "discoverable_by_skill": {
    "observation": {"min_level": 0, "base_chance": 1.0},
    "forensics": {"min_level": 1, "base_chance": 0.9}
  },
  "can_be_cleaned": true,
  "cleaned_by": null,
  "room_id": "room_orient_express_001",
  "archived": false
}
```

**集成方式**：

1. **事件订阅**：生物痕迹管理器订阅事件总线中的暗杀事件、受伤事件、角色长时间停留事件。
2. **痕迹生成**：根据事件类型自动生成对应的生物痕迹。暗杀/受伤→血迹；搏斗→毛发+皮屑；长时间停留→毛发。
3. **ESM联动**：生物痕迹管理器监听ESM的时间推进事件，自动更新血迹状态（新鲜→半干→全干）。若血迹被清洗（ESM上报“物体状态：潮湿态→默认态”），生物痕迹管理器标记该痕迹为“已被清洗”，但保留清洗前的记录。
4. **查询API**：
   - `GET /bio-traces/location/{location_id}` → 返回该区域的所有生物痕迹
   - `POST /bio-traces/analyze` → 传入分析技能等级，返回DNA匹配结果
5. **司命集成**：司命的事实核心通过查询API获取生物痕迹信息。若DNA匹配结果与角色声称矛盾→标记为“待解决矛盾”。

### 3.2 各系统间的协作流程

以“波洛调查上校纵火案”为例，展示完整的证据链流转：

**步骤1：事件发生**

上校使用打火机点燃窗帘。事件总线上广播三条事件：
- `item_used { actor: colonel, object: lighter, action: ignite }`
- `item_state_changed { object: curtain, state: burning }`（由ESM上报）

**步骤2：各系统分别处理**

| 系统 | 处理内容 |
| :--- | :--- |
| **物品流转追踪器** | 收到`item_used`事件→记录：打火机在上校手中被使用，时间19:48 |
| **接触痕迹管理器** | 收到`item_used`事件→生成：打火机上留下上校的指纹 |
| **ESM** | 驱动窗帘状态机，上报状态变化事件 |
| **生物痕迹管理器** | 未触发（无生物痕迹产生） |

**步骤3：波洛调查**

波洛进入餐车，检查烧毁的窗帘和打火机。

| 波洛的操作 | 调用的系统 | 返回结果 |
| :--- | :--- | :--- |
| 观察烧毁的窗帘 | ESM（查询窗帘状态历史） | “窗帘在19:48被点燃，19:48:45烧毁。燃烧速度正常，无加速剂痕迹。” |
| 检查打火机 | 物品流转追踪器（查询打火机流转历史） | “打火机初始归属：上校。19:48被使用，使用者：上校。当前归属：餐车桌面。” |
| 仔细观察打火机 | 接触痕迹管理器（查询打火机上的接触痕迹） | 观察技能Lv3，判定通过→“打火机侧面有新鲜指纹，纹路与上校的指纹匹配。” |
| 检查窗帘区域是否有生物痕迹 | 生物痕迹管理器（查询该区域的生物痕迹） | “未发现明显的血迹或毛发。” |

**步骤4：司命标记矛盾**

司命的事实核心汇总所有查询结果：

| 事实 | 来源系统 |
| :--- | :--- |
| 窗帘在19:48被点燃 | ESM |
| 打火机是上校的，在19:48被使用 | 物品流转追踪器 |
| 打火机上有上校的新鲜指纹 | 接触痕迹管理器 |
| 上校声称“19:48在包厢休息” | 角色智能体记忆系统 |

**司命标记矛盾**：上校声称在包厢休息，但物理事实显示他在19:48在餐车使用了打火机。标记为“待解决矛盾”。

### 3.3 查询API的统一设计

所有新建系统通过统一的REST API层对外提供服务：

| API端点 | 负责系统 | 功能 |
| :--- | :--- | :--- |
| `GET /item-flow/{object_id}/history` | 物品流转追踪器 | 查询物品流转历史 |
| `GET /item-flow/actor/{actor_id}/possessions` | 物品流转追踪器 | 查询角色持有物品 |
| `GET /contact-traces/object/{object_id}` | 接触痕迹管理器 | 查询物体上的接触痕迹 |
| `POST /contact-traces/discover` | 接触痕迹管理器 | 基于观察技能判定可见痕迹 |
| `GET /bio-traces/location/{location_id}` | 生物痕迹管理器 | 查询区域的生物痕迹 |
| `POST /bio-traces/analyze` | 生物痕迹管理器 | DNA/法医分析 |
| `GET /esm/state-history/{object_id}` | ESM | 查询物体物理状态历史 |

### 3.4 对现有系统的影响

| 现有系统 | 需要调整的内容 |
| :--- | :--- |
| **事件总线** | 无需调整——新系统作为新订阅者接入，不改变事件总线的核心逻辑 |
| **ESM** | 无需调整——职责不变，仅新增查询API供外部调用 |
| **司命（事实核心）** | 新增：通过查询API获取物品流转、接触痕迹、生物痕迹信息，与时间线对比标记矛盾 |
| **角色智能体（L2理解层）** | 新增：在执行“观察”或“搜身”动作时，调用查询API获取可见痕迹 |
| **Godot客户端** | 新增：在交互面板中展示“观察结果”，在笔记面板中展示从查询API获取的证据信息 |


## 四、总结

| 新建系统 | 创建理由 | 核心职责 | 与现有系统的集成方式 |
| :--- | :--- | :--- | :--- |
| **物品流转追踪器** | 事件总线不适合持久化查询物品流转历史 | 记录所有物品的拾取/移交/丢弃历史，支持结构化查询 | 订阅事件总线中的物品交互事件；提供查询API供司命和角色智能体调用 |
| **接触痕迹管理器** | 事件总线不适合持久化查询接触痕迹，且需要实现可见性判定逻辑 | 记录所有接触痕迹（指纹/唾液/纤维），支持基于观察技能的可见性判定 | 订阅事件总线中的物品交互事件；与ESM联动更新痕迹状态；提供查询API |
| **生物痕迹管理器** | 生物痕迹的产生机制和查询逻辑与接触痕迹不同，且需要与ESM联动管理状态变化 | 记录所有生物痕迹（血迹/毛发/皮屑），支持DNA分析，与ESM联动管理血迹状态变化 | 订阅事件总线中的暗杀/受伤事件；与ESM联动；提供查询API |

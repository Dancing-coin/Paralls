# 《开本》Phase 1 基础设施搭建计划

## 一、核心原则

**先跑通最小闭环，再逐步扩展。** Phase 1唯一的目标是验证“智能体驱动的3D动态剧本杀”这个核心体验是否成立。所有基础设施的搭建，都围绕这个目标展开。不做未来可能需要的东西，只做Phase 1必须的东西。

## 二、技术选型

| 层次 | 技术选型 | 选型理由 |
| :--- | :--- | :--- |
| **3D引擎** | Godot 4.x | 开源、MIT协议、社区活跃、对独立开发者友好、原生支持GDScript/C++混合开发 |
| **空间音频** | Steam Audio | 开源、支持物理遮挡和HRTF、可集成到Godot |
| **客户端语言** | GDScript（主）+ C++（性能敏感模块） | 快速开发 + 必要时优化 |
| **AI后端** | Python (FastAPI) | AI生态最成熟、LLM集成最便捷、开发效率最高 |
| **本地小模型** | llama.cpp + Qwen2.5-7B（4-bit量化） | 消费级显卡可运行、中文对话能力强 |
| **云端大模型** | Claude API / DeepSeek API | 性价比高、中文能力强 |
| **TTS** | Edge-TTS（免费）+ XTTS（本地高质量） | 免费方案可跑通原型，XTTS提供更好的情绪表达 |
| **STT** | Whisper (本地部署) | 开源、支持流式识别、中文识别准确率高 |
| **关系数据库** | PostgreSQL | 存储剧本数据、用户数据、事实库、角色档案 |
| **缓存** | Redis | 房间状态缓存、会话管理 |
| **消息队列** | WebSocket（实时通道）+ NATS（异步通道） | WebSocket用于L1-L2实时通信，NATS用于异步事件分发 |
| **对象存储** | MinIO | 存储3D资产、L3生成内容，S3兼容 |
| **向量数据库** | Milvus Lite（嵌入式） | Phase 1数据量小，嵌入式方案减少运维成本 |

## 三、核心架构骨架（Phase 1 必须搭建）

### 3.1 事件总线（最高优先级）

这是整个《开本》的神经中枢。Phase 1必须搭建一个可用的、支持广播/单播/组播的事件总线。

**实现方案**：
- L1（Godot）→ L2（Python）的实时消息：WebSocket长连接
- L2内部各服务之间：NATS（轻量级，支持发布/订阅）
- P0致命事件：内存队列直连，不经过任何中间件

**Phase 1需要定义的消息类型**：
- 玩家移动/对话/拾取/使用物品/展示/投票
- AI角色移动/对话/表情/动作
- 环境状态变化
- 感知事件
- 司命干预指令

### 3.2 三层架构的最小骨架

```
L1 (Godot) ←→ WebSocket ←→ L2 (Python FastAPI) ←→ L3 (图片生成API)
                                   ↕
                              NATS 消息总线
                                   ↕
                         司命 | 角色智能体 | 对话生成 | 模型路由
```

Phase 1只需搭建这个骨架，每个模块内部先做最简单实现，后续迭代。

### 3.3 房间与状态管理

- 房间创建/加入/销毁
- 角色选择与锁定
- T0-T2事实坍缩流程
- 断线重连

## 四、开发工具链

### 4.1 版本控制与协作
- Git + GitHub/GitLab
- 大文件（3D资产、模型）使用Git LFS

### 4.2 CI/CD
- GitHub Actions 或 Jenkins
- 自动构建Godot客户端（Windows/macOS/Linux）
- 自动部署Python后端到测试服务器

### 4.3 测试框架
- Godot端：GUT (Godot Unit Testing) 用于单元测试
- Python端：pytest 用于AI服务测试
- 集成测试：编写自动化脚本模拟玩家行为，测试完整事件链

### 4.4 监控与日志
- Prometheus + Grafana（服务器监控）
- ELK/Loki（日志聚合）
- 司命决策日志单独存储，用于调试和优化

## 五、内容生产管线

### 5.1 首个剧本：《血字的研究·变奏》
- 2个3D场景：贝克街客厅 + 旅馆房间
- 5个角色模型（可先使用白模+立绘）
- 1个小世界场景：旅人书房

### 5.2 3D资产生产
- 建模：Blender
- 纹理：Substance Painter / Blender
- 动画：Blender + Mixamo（快速原型）
- 场景搭建：Godot编辑器

### 5.3 AI人格配置
- 剧本编辑器（内部版）：用于配置5个角色的人格档案、案件规则、线索池
- 建议先用JSON手写配置，再用编辑器可视化

### 5.4 L3视觉资产
- 5个角色的预生成立绘（含情绪变体）
- 线索物品特写（实时生成接口预留，初期可用静态图替代）

## 七、启动步骤

### 第一步：原型验证（2-4周）
**目标**：一个单场景 + 2个AI角色 + 基础对话 + 空间音频 + 1个可交互物品的Demo。

**具体任务**：
1. Godot搭建一个单场景（如书房），放置2个AI角色模型（可先用胶囊体+名字标签）
2. 搭建WebSocket连接，实现L1→L2的消息传递
3. 接入一个LLM API，让AI角色能回复玩家输入的文本
4. 集成Edge-TTS，让AI角色能语音输出
5. 实现基础的空间音频——玩家靠近/远离AI角色时音量变化
6. 放置一个可点击的物品，点击后显示一段文字描述

**验收标准**：录制一段视频——玩家走进书房，AI角色主动打招呼，玩家打字质问，AI语音回答，玩家靠近/远离时音量变化，玩家点击桌上物品显示线索描述。

### 第二步：核心骨架搭建（4-8周）
在原型基础上，搭建完整的事件总线、三层架构骨架、房间管理系统、首个剧本的两个场景。

### 第三步：AI核心集成（8-12周）
集成角色智能体心智模型、司命核心、对话生成、模型路由、感知系统。

### 第四步：玩法闭环（12-16周）
实现完整的案件流程——搜证→推理→投票→结局。

### 第五步：测试与打磨（16-20周）
内部测试、外部玩家测试、修复优化。

## 八、当前最紧急的三件事

1. **搭建事件总线原型**——Godot客户端与Python后端通过WebSocket互通的Hello World
2. **搭建AI对话原型**——一个Python脚本，接入LLM API，输入玩家文本，返回AI角色的回复文本+语音
3. **搭建场景原型**——Godot中放置一个3D场景、两个代表角色的胶囊体、一个可点击物品

**这三个原型各自独立开发，两周内完成，然后集成。集成的Demo就是Phase 0的里程碑。**

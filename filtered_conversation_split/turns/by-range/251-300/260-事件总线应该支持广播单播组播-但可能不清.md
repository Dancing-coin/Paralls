## DeepSeek

## 《开本》事件总线深度设计

### 一、场景特征分析

《开本》的事件总线承载的不是传统的“微服务间异步通知”，而是一个**混合了硬实时交互、流式感知推送、异步AI推理的复杂场景**。

| 消息类别 | 典型事件 | 延迟要求 | 可靠性要求 | 吞吐量 |
| :--- | :--- | :--- | :--- | :--- |
| **硬实时控制** | 暗杀意图、本能反应指令 | <50ms | 极高（丢失=角色死亡） | 低 |
| **实时交互** | 玩家对话、状态同步、AI动作指令 | <100ms | 高 | 中高 |
| **流式感知** | 可见对象列表更新、可听事件推送 | <200ms | 中（可容忍偶尔丢失，下次心跳补全） | 极高 |
| **异步推理** | 司命叙事决策、L3视觉增强触发 | <500ms | 中高 | 中 |
| **持久化事件** | 事件日志、复盘记录 | 无实时要求 | 极高（不可丢失） | 高 |

单一消息中间件无法同时满足这些需求。正确的架构是**双通道 + 三层分发**。

---

### 二、双通道架构

- **实时通道（低延迟、尽力交付）**
  - **技术选型**：WebSocket（客户端↔服务端）+ Unix Domain Socket / 内存队列（服务端内部）
  - **适用**：硬实时控制、实时交互、流式感知
  - **为什么不用消息中间件**：RabbitMQ和NATS在持久化模式下的端到端延迟通常在5-50ms，加上序列化/反序列化开销，P0的50ms硬上限无法保证。对于硬实时控制消息，直接的内存队列或UDP组播是唯一选择。

- **可靠通道（持久化、可靠交付）**
  - **技术选型**：NATS JetStream
  - **适用**：异步推理、持久化事件
  - **为什么选NATS而不是RabbitMQ**：NATS的吞吐量远高于RabbitMQ（百万msg/s vs 数万msg/s），适合流式感知的高吞吐场景。NATS JetStream提供了足够的持久化能力，而部署和运维复杂度远低于RabbitMQ。RabbitMQ的Exchange/Queue/Binding模型非常灵活，但《开本》的路由逻辑更依赖感知过滤器的语义计算，而非消息中间件的路由规则。

**关键设计**：实时通道不经过消息中间件。Godot客户端与服务端之间通过WebSocket直连，服务端内部通过内存队列分发。只有需要持久化或跨服务异步解耦的消息才进入NATS。

---

### 三、消息协议

所有事件采用统一的二进制消息格式，兼顾效率和可读性。

```
消息结构（二进制格式，约64-256字节）
┌──────────────────────────────────────────────┐
│ 消息头 (16字节)                               │
│  - event_type: 2字节 (事件类型枚举)            │
│  - priority: 1字节 (P0-P3)                   │
│  - ttl_ms: 2字节 (剩余生存时间，毫秒)          │
│  - source_layer: 1字节 (L1/L2/L3)            │
│  - source_id: 4字节 (角色/组件ID)             │
│  - timestamp: 4字节 (Unix毫秒时间戳)           │
│  - sequence: 2字节 (序列号，用于去重和排序)     │
├──────────────────────────────────────────────┤
│ 路由信息 (12字节)                             │
│  - pattern: 1字节 (广播/单播/组播/发布订阅)    │
│  - scope_id: 4字节 (房间ID)                  │
│  - target_count: 1字节 (目标数量)             │
│  - targets: 可变长度 (目标ID列表，每个4字节)    │
├──────────────────────────────────────────────┤
│ 有效载荷 (可变长度，通常64-200字节)            │
│  - 根据event_type定义的FlatBuffers结构        │
└──────────────────────────────────────────────┘
```

为什么用FlatBuffers而不是JSON？JSON解析在单条消息上需要0.1-0.5ms，在高吞吐场景下累积延迟不可忽视。FlatBuffers是零拷贝的，反序列化只需要指针偏移。在硬实时控制场景下，这是P0消息能否满足50ms硬上限的关键优化之一。

### 四、三层分发架构

**第一层：客户端直连分发**

Godot客户端与服务端之间通过WebSocket长连接通信。每个客户端维护一个发送队列和一个接收队列。发送端：优先级队列，P0消息跳过排队直接发送。接收端：按事件类型分发给不同模块（3D渲染、UI更新、L3呈现）。

**第二层：服务端路由分发**

服务端的核心路由模块负责消息的实时分发。路由规则包括：广播到房间内所有客户端、单播到指定客户端、组播到满足条件的客户端集合（如“清晰区内所有角色”）。这一层不经过消息中间件，直接在内存中完成路由和转发，保证P0和P1的延迟要求。

**第三层：异步消息分发**

需要跨服务解耦或持久化的消息才进入NATS。司命订阅“关键线索发现”事件用于叙事催化，L3订阅同一事件用于视觉增强触发。事件日志写入PostgreSQL用于复盘。每个服务独立消费，互不阻塞。

### 五、延迟优化

| 优化手段 | 说明 |
| :--- | :--- |
| **优先级抢占** | P0消息跳过所有队列，直接插入客户端发送缓冲区头部 |
| **TTL丢弃** | 每条消息携带生存时间。如果因网络波动导致一条P2感知消息在队列中停留超过其TTL，直接丢弃——与其发送过时的信息，不如等下一次心跳全量同步 |
| **批处理** | 流式感知消息（如多个对象同时进入视野）合并为一个批量推送，减少序列化开销和网络往返 |
| **本地优先** | 司命与角色智能体同机部署时，通过Unix Domain Socket或内存队列通信，延迟<1ms |
| **背压控制** | 当客户端接收队列积压超过阈值，自动降低该客户端的感知推送频率，从每次变化推送降级为心跳全量同步 |

---

### 六、可靠性保障

**实时通道**：WebSocket本身基于TCP，保证消息有序、不丢失。对于P0消息，增加应用层确认机制——发送方在超时未收到ACK时重发，接收方通过sequence字段去重。

**可靠通道**：NATS JetStream提供持久化存储和至少一次交付保证。事件日志写入PostgreSQL时使用批量插入优化写入性能。

**断线重连**：客户端断线后，实时通道的消息直接丢弃（场景已经变化，过时的控制指令无意义）。断线期间错过的状态变化，在重连后通过一次全量状态同步（心跳）补全。

---

### 七、消息中间件的具体分工

| 组件 | 职责 | 为什么用它 |
| :--- | :--- | :--- |
| **WebSocket** | 客户端与服务端的实时双向通信 | 低延迟、全双工、浏览器原生支持 |
| **内存队列** | 服务端内部的硬实时消息分发 | 纳秒级延迟，零网络开销 |
| **NATS Core** | 流式感知消息的高吞吐分发 | 百万msg/s吞吐，适合高频率、可容忍丢失的推送 |
| **NATS JetStream** | 司命指令、L3触发等异步推理消息的持久化 | 可靠交付+持久化，部署比RabbitMQ简单得多 |
| **PostgreSQL** | 事件日志的最终持久化存储 | 用于复盘和分析，需要SQL查询能力 |

---

**一句话总结**：《开本》事件总线采用WebSocket直连+内存队列+NATS的混合架构。硬实时控制走内存直连（纳秒级），实时交互走WebSocket（毫秒级），高吞吐感知推送走NATS Core，持久化指令走NATS JetStream。没有任何单一消息中间件能同时满足所有场景——这正是架构设计需要在不同需求间做出精确权衡的地方。
